===================

php2shell-scanner: high-fidelity exposure detection for CVE-2026-109618 and CVE-2026-109619

Searchlight Cyber's research team (the group formerly known as Assetnote) released an open-source scanner for the php2shell vulnerability pair. The team has been through this cycle before, both with wp2shell, which it discovered itself, and with react2shell late last year. Each of these high-impact web-stack issues raises the same detection problem: maximize coverage while minimizing false positives and false negatives. This release is their answer for the current one.

Why another scanner

Scanners published in the wake of the disclosure mostly rely on version checks, or fail to represent the vulnerable conditions accurately for both mod_php and php-fpm. Version-only signals fail in two directions: flagging hosts that are actually patched, or missing hosts where the banner does not reflect exploitable conditions. The logic was first implemented inside the Searchlight Exposure platform, and the standalone version is now public.

How the check works

Detection is progressive, in three tiers:

1. Controlled OOM trigger. The scanner attempts to produce a PHP memory-exhaustion error. The vulnerability fundamentally requires an out-of-memory condition, so there is no reliable way to confirm exploitability without inducing it.
2. Differential empty HTTP 500. Next, it observes responses for a differential empty HTTP 500, which the authors describe as a PHP-FPM worker failure.
3. Version fallback. Only when behavioral checks do not settle the question does it fall back to whether the target advertises a known unpatched PHP version.

Risk profile

The authors are direct about this: triggering an OOM condition is inherently risky, and that is the price of reliable detection here. In the majority of PHP installations a worker crash recovers quickly and should not cause disruption, but the writeup explicitly asks for care and caution when scanning. Practical translation: don't fire this at capacity-constrained production systems during peak traffic.

Context around the disclosure

Initial information on the vulnerability was incomplete, followed quickly by a wave of auto-generated, low-quality PoCs that added noise rather than clarity. Searchlight credits Calif's writeup with settling most of the open questions. The detection logic served Searchlight Exposure customers first, then was released publicly so anyone can determine exposure with the same rigor.

Practical notes
• Exposure validation across mixed PHP estates where mod_php and php-fpm behave differently
• Prioritization: behavioral tiers are stronger evidence than version matches
• Scheduling: run behavioral checks away from peak load, and treat the version fallback tier as weaker evidence by design
• The tool is newly released and not personally tested; this summary reflects the vendor writeup, not an independent accuracy assessment

🛠️ Tool
===================

php2shell-scanner: high-fidelity exposure detection for CVE-2026-109618 and CVE-2026-109619

Searchlight Cyber's research team (the group formerly known as Assetnote) released an open-source scanner for the php2shell vulnerability pair. The team has been through this cycle before, both with wp2shell, which it discovered itself, and with react2shell late last year. Each of these high-impact web-stack issues raises the same detection problem: maximize coverage while minimizing false positives and false negatives. This release is their answer for the current one.

Why another scanner

Scanners published in the wake of the disclosure mostly rely on version checks, or fail to represent the vulnerable conditions accurately for both mod_php and php-fpm. Version-only signals fail in two directions: flagging hosts that are actually patched, or missing hosts where the banner does not reflect exploitable conditions. The logic was first implemented inside the Searchlight Exposure platform, and the standalone version is now public.

How the check works

Detection is progressive, in three tiers:

1. Controlled OOM trigger. The scanner attempts to produce a PHP memory-exhaustion error. The vulnerability fundamentally requires an out-of-memory condition, so there is no reliable way to confirm exploitability without inducing it.
2. Differential empty HTTP 500. Next, it observes responses for a differential empty HTTP 500, which the authors describe as a PHP-FPM worker failure.
3. Version fallback. Only when behavioral checks do not settle the question does it fall back to whether the target advertises a known unpatched PHP version.

Risk profile

The authors are direct about this: triggering an OOM condition is inherently risky, and that is the price of reliable detection here. In the majority of PHP installations a worker crash recovers quickly and should not cause disruption, but the writeup explicitly asks for care and caution when scanning. Practical translation: don't fire this at capacity-constrained production systems during peak traffic.

Context around the disclosure

Initial information on the vulnerability was incomplete, followed quickly by a wave of auto-generated, low-quality PoCs that added noise rather than clarity. Searchlight credits Calif's writeup with settling most of the open questions. The detection logic served Searchlight Exposure customers first, then was released publicly so anyone can determine exposure with the same rigor.

Practical notes
• Exposure validation across mixed PHP estates where mod_php and php-fpm behave differently
• Prioritization: behavioral tiers are stronger evidence than version matches
• Scheduling: run behavioral checks away from peak load, and treat the version fallback tier as weaker evidence by design
• The tool is newly released and not personally tested; this summary reflects the vendor writeup, not an independent accuracy assessment

Security Advisory: CVE-2025-71438 - Out-of-Bounds Read in GPAC/MP4Box

Processing a crafted AC-4 stream with an invalid `frame_rate_index` triggers an out-of-bounds read in `gf_odf_ac4_cfg_dsi_v1`, causing MP4Box to crash.

Summary:
The `gf_odf_ac4_cfg_dsi_v1` function in `odf/descriptors.c` uses a stream-supplied `frame_rate_index` to index into fixed-size lookup tables (`AC4_SAMPLE_DELTA_TABLE_48`, `AC4_MEDIA_TIMESCALE_48`). The function does not validate that the index is within bounds before performing the table lookup. A crafted AC-4 file carrying an out-of-range index (e.g., 15) causes an out-of-bounds read, ultimately resulting in a NULL dereference and process crash.

CWE:
CWE-125 - Out-of-bounds Read

Affected Component:
```
odf/descriptors.c:2179
Function: gf_odf_ac4_cfg_dsi_v1()
```

Affected Product:
MP4Box (GPAC Multimedia Open Source Project)

Affected Version:
2.5-DEV-rev1617-g856674b22-master; commit `856674b226d6cbe28a941ad223be38194cbf7d37`. Any codebase equivalent to this commit that has not applied the fix commit is affected.

Attack Conditions:
An attacker supplies a specially crafted AC-4 stream file containing an invalid `frame_rate_index` value. Local access is required; the victim must invoke `MP4Box -dash 100 <crafted_file>` or any equivalent DASH segmentation command that triggers the AC-4 configuration descriptor parsing path.

Impact:
The out-of-bounds read leads to an immediate process crash (SEGV READ at address 0x000000000000), resulting in Denial of Service. No evidence of arbitrary code execution was observed.

Fix / mitigation status:
The issue was fixed in GPAC commit:
```
13eb5b76560aaf7813b865a2ad433258478e2695
```
Users should update to a GPAC build containing this commit or later.

@lienrag @mgorny Normally, when you use pip to install packages, it installs the latest versions that satisfies “the given constraints”. These certainly include constraints given on the command line; whether this also includes dependency metadata of packages already installed inside the venv in use, I'm not sure (would have to check).

Anyway, there are circumstances in which developers want to have an easy way to install a set of packages with clearly defined versions (to have things reproducible, especially when the venv creation is automated). This is what lock files do: they record the versions of the packages you want to “pin” (normally, compatible versions!). Of course, you need to update the lock file when there is a security update for one of the locked packages, or it will be blocked...

The link given earlier by @mgorny is full of expert advice. If you don't want to micro-manage your venvs, I believe the following should be safe:

  1. Make sure your distro has patched everything related to these problems (in particular, that the distro-shipped pip doesn't use the compromised CA certificates).

  2. Delete your existing venvs (I assume they contain no interesting data, only installed packages).

  3. Recreate them in a way that does not force vulnerable versions to be installed: should be fine unless you use lock files or otherwise hardcode version requirements.
