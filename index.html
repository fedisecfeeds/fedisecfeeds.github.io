Malcolm v26.10.0

Malcolm v26.10.0 moves Zeek to 9.0.1 LTS, expands threat intelligence enrichment with MITRE ATT&CK context, aligns Zeek OT protocol fields with Arkime, and fixes nine Malcolm security issues. Uploaded PCAP processing gets two important correctness fixes, and nearly every external artifact used in the build is now pinned and verified.

Upgrading: if you are upgrading an existing install, run ./scripts/status first so Malcolm can migrate settings before you run ./scripts/configure, ./scripts/start, or other control scripts.

  • Full changelog: v26.09.0...v26.10.0

✨ Features and enhancements

  • Zeek 9.0.1 LTS. multicast_participants.log is parsed and shown in a new Multicast dashboard. ntp_control.log and ntp_private.log are parsed and indexed. (#1119)
  • OT field normalization. Zeek fields for BACnet, C12.22, DNP3, ENIP/CIP, Modbus, OPC UA, S7comm, and Synchrophasor are copied to Arkime's field names, so filters and drill-downs carry between Dashboards and Arkime. Original zeek.* fields are kept. (#1257)
  • Threat intel in ECS threat.* fields. Zeek intel kill chain phases, MISP MITRE galaxy tags, Mandiant and Google Threat Intelligence actors, Suricata ET mitre_* metadata, and capa results all map to normalized tactic, technique, subtechnique, and group fields. ATT&CK for ICS is told apart from Enterprise. (#695)
  • Richer indicator metadata. Mandiant categories, campaigns, reports, and threat score, plus STIX 2.1 confidence, now reach Zeek intel. Google Threat Intelligence collections accept ioc_types and include_autogenerated_tags to cut memory use.
  • Community ID in Logstash for Zeek logs that arrive without one, controlled by LOGSTASH_ZEEK_COMPUTE_COMMUNITY_ID (on by default). (#400)
  • API document lookup gains sort, offset, track_total_hits, and a total hit count. It and field aggregations now return shards and timed_out, so a partial or timed-out search no longer looks like an empty result. Bad arguments return HTTP 400. (#1130, #1131)
  • Custom ports for 13 ICSNPP analyzers through new ZEEK_PORTS_* variables. Three older variables are renamed to match, with values migrated on upgrade. (#1272)
  • NetBox skips the device-type library import once it has completed for a revision. NETBOX_DEVICETYPE_IMPORT_VENDORS can limit the first import, which also limits MAC OUI matching.
  • Smaller items: a low-RAM warning during configuration, a Hedgehog ISO prompt for the status kiosk, restyled account management pages, and Biomes dashboard docs in Analytics.
  • New Corelight Zeek detections: php2shell-detect and emudhra-weak-keys.

🛡️ Security remediation and hardening

  • Stored XSS in the file-upload container let a user with upload access run JavaScript in another user's session. The patch route also allowed writes to arbitrary directories. The read side is gone, the vulnerable handlers are stripped at build time, and responses carry nosniff and a strict CSP. (GHSA-qv8w-m37v-6c7j)
  • Credential disclosure in the hh-extracted-files proxy, which forwarded the caller's auth headers and cookies to a caller-chosen destination. Those headers are now cleared. (GHSA-325g-72fr-vj2x)
  • The published default Arkime WISE PIN and viewer password secret are removed. (GHSA-w2jh-h3pq-273j)
  • MaxMind and GitHub tokens are passed as BuildKit secrets instead of build arguments. Exposed MaxMind credentials were rotated. (GHSA-3293-9mf2-qf68)
  • Logstash's Beats input requires a client certificate when BEATS_SSL=true. (GHSA-f2gq-m4v3-2383)
  • The root-run PCAP upload watcher no longer follows symlinks. (GHSA-98jw-5wq7-6qjv)
  • Every outbound API request now has a timeout, and the API runs multiple workers, so one hung dependency can't take it down. (GHSA-x9f2-h2rj-vp63)
  • nginx/htpasswd and htadmin/metadata are tightened to 0640. (GHSA-rxpm-f8cm-2m5m)

PHP2Shell: One Vulnerable PHP Server Can Become Your Next Major Security Incident

The vulnerability is in PHP. The real failure may be in your IT operations.

On October 21, 2026, security researchers disclosed two critical vulnerabilities in PHP that can allow an unauthenticated attacker to execute code remotely. Within days, exploitation reports emerged, and CISA added both vulnerabilities to its Known Exploited Vulnerabilities catalog.

The vulnerabilities, tracked as CVE-2026-109618 and CVE-2026-109619, are collectively known as PHP2Shell. Both received a CVSS 4.0 severity score of 9.2. PHP is widely deployed, making the potential attack surface enormous.

This isn’t a theoretical risk to put on next quarter’s security roadmap.
It’s an operational problem that needs attention now.

Why PHP2Shell is different

Most people hear about a vulnerability and immediately ask: Which application is affected?

PHP2Shell changes the conversation because the flaw sits in the PHP runtime itself, below application-level defenses.

The vulnerabilities involve memory-management errors that can leave PHP in an unsafe state when handling requests. Under the right conditions, an attacker can exploit that behavior to execute arbitrary code or expose sensitive process memory.

An attacker doesn’t necessarily need a valid account or a compromised employee laptop. A vulnerable, internet-facing PHP service may be enough.

And the implications go beyond the web application itself. Successful remote code execution can give an attacker a foothold to steal credentials, access sensitive files, establish persistence, or move toward other systems.

The critical detail: an application-level security check cannot reliably protect against a vulnerability that can be triggered before application code runs.

That is why PHP2Shell requires infrastructure-level remediation, not simply a code change in your application.

The uncomfortable question: Do you know where you’re running PHP?

PHP is not limited to the application your engineering team actively maintains.

It may be running in a WordPress installation, a legacy internal tool, a customer portal, a third-party application, a container, or a server that nobody remembers deploying.

The affected environments include PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, and LiteSpeed. The PHP team has identified Apache mod_php as particularly concerning.

For a 50- or 200-person company without a large security team, the difficult part may not be understanding the vulnerability. It may be answering five basic questions:

  • Which internet-facing systems run PHP?
  • Which versions are installed, including bundled and containerized versions?
  • Who owns each system, and who can patch it?
  • Have the vulnerable systems actually been updated and restarted?
  • Has anything suspicious happened since the vulnerability became exploitable?

If those answers require days of Slack messages and spreadsheet archaeology, your company has an operational security gap.

What companies should do now

1. Find every affected PHP installation

Inventory production servers, development environments, containers, hosted applications, and third-party software that bundles PHP.

Don’t rely on the engineering team’s memory or a list of approved assets. Verify the running versions and configurations.

2. Patch to a fixed release

The PHP security releases addressing the two PHP2Shell vulnerabilities are:

  • PHP 8.5.12 or later
  • PHP 8.4.27 or later
  • PHP 8.3.36 or later
  • PHP 8.2.35 or later

These are the minimum fixed releases for the respective branches; use the latest supported security release available. PHP 8.1 and older branches are end-of-life and require migration to a supported version.

Verify the actual runtime, deploy the appropriate update, restart affected services where necessary, and confirm that the fix is active. Updating a development dependency doesn’t patch a production server. If you cannot patch immediately, restrict exposure and apply the PHP team’s recommended temporary mitigations. Disabling session upload-progress tracking can reduce risk, but it is not a substitute for installing the security update.

Important: A separate PHP issue, CVE-2026-115560, was disclosed shortly afterward. It involves a specific combination of session configuration and application behavior and is not fixed by the PHP2Shell releases above. Check the latest PHP security advisories rather than assuming one update resolves every newly disclosed PHP vulnerability.

3. Look for signs of compromise

Patching closes the known vulnerability. It does not prove that nobody exploited it before the update.
Review web-server, application, authentication, and endpoint telemetry for suspicious activity. Pay particular attention to unexpected child processes launched by PHP workers, unfamiliar files, new accounts, unusual outbound connections, and unexplained changes to services.

Don’t rely exclusively on matching a known malicious request. Exploitation can be difficult to identify from application logs alone, especially when the vulnerable behavior occurs before application code executes. If you find evidence of compromise, treat it as an incident: investigate the host, contain the threat, assess credential exposure, and follow an appropriate recovery process.

4. Turn the response into a repeatable process

PHP2Shell is one example of a recurring problem: a critical vulnerability is disclosed, and every organization must quickly discover its exposure, assign ownership, remediate affected systems, and document the outcome.
The companies that handle this well aren’t necessarily the ones with the largest security budgets. They are the ones that can answer those questions quickly and consistently.

PHP2Shell: One Vulnerable PHP Server Can Become Your Next Major Security Incident

The vulnerability is in PHP. The real failure may be in your IT operations.

On October 21, 2026, security researchers disclosed two critical vulnerabilities in PHP that can allow an unauthenticated attacker to execute code remotely. Within days, exploitation reports emerged, and CISA added both vulnerabilities to its Known Exploited Vulnerabilities catalog.

The vulnerabilities, tracked as CVE-2026-109618 and CVE-2026-109619, are collectively known as PHP2Shell. Both received a CVSS 4.0 severity score of 9.2. PHP is widely deployed, making the potential attack surface enormous.

This isn’t a theoretical risk to put on next quarter’s security roadmap.
It’s an operational problem that needs attention now.

Why PHP2Shell is different

Most people hear about a vulnerability and immediately ask: Which application is affected?

PHP2Shell changes the conversation because the flaw sits in the PHP runtime itself, below application-level defenses.

The vulnerabilities involve memory-management errors that can leave PHP in an unsafe state when handling requests. Under the right conditions, an attacker can exploit that behavior to execute arbitrary code or expose sensitive process memory.

An attacker doesn’t necessarily need a valid account or a compromised employee laptop. A vulnerable, internet-facing PHP service may be enough.

And the implications go beyond the web application itself. Successful remote code execution can give an attacker a foothold to steal credentials, access sensitive files, establish persistence, or move toward other systems.

The critical detail: an application-level security check cannot reliably protect against a vulnerability that can be triggered before application code runs.

That is why PHP2Shell requires infrastructure-level remediation, not simply a code change in your application.

The uncomfortable question: Do you know where you’re running PHP?

PHP is not limited to the application your engineering team actively maintains.

It may be running in a WordPress installation, a legacy internal tool, a customer portal, a third-party application, a container, or a server that nobody remembers deploying.

The affected environments include PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, and LiteSpeed. The PHP team has identified Apache mod_php as particularly concerning.

For a 50- or 200-person company without a large security team, the difficult part may not be understanding the vulnerability. It may be answering five basic questions:

  • Which internet-facing systems run PHP?
  • Which versions are installed, including bundled and containerized versions?
  • Who owns each system, and who can patch it?
  • Have the vulnerable systems actually been updated and restarted?
  • Has anything suspicious happened since the vulnerability became exploitable?

If those answers require days of Slack messages and spreadsheet archaeology, your company has an operational security gap.

What companies should do now

1. Find every affected PHP installation

Inventory production servers, development environments, containers, hosted applications, and third-party software that bundles PHP.

Don’t rely on the engineering team’s memory or a list of approved assets. Verify the running versions and configurations.

2. Patch to a fixed release

The PHP security releases addressing the two PHP2Shell vulnerabilities are:

  • PHP 8.5.12 or later
  • PHP 8.4.27 or later
